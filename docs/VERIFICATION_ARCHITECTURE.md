# Архитектура верификации: c2pax Verification Architecture

Документ описывает подсистему криптографической проверки, управление доверенными сертификатами (TrustStore), применение политик (VerificationPolicy) и формирование вердиктов валидации.

---

## 1. Модель верификации

Верификация C2PA манифеста состоит из трёх независимых уровней проверок:

```
                  ┌──────────────────────────────┐
                  │        Asset Source          │
                  └──────────────┬───────────────┘
                                 │
                 [ Уровень 1: Проверка формата ]
                 • Валидность JUMBF / CBOR контейнера
                 • Отсутствие бинарных повреждений
                                 │
                 [ Уровень 2: Целостность (Integrity) ]
                 • Сверка хэшей контента с утверждениями манифеста
                 • Проверка подписи клейма (Claim Signature)
                                 │
                 [ Уровень 3: Доверие (Trust & Policy) ]
                 • Сопоставление сертификата подписанта с TrustStore
                 • Проверка временных меток (TSA / RFC 3161)
                 • Проверка срока действия сертификата
                 • Применение настраиваемой VerificationPolicy
                                 │
                  ┌──────────────▼───────────────┐
                  │      VerificationResult      │
                  │   (status, valid, explain)   │
                  └──────────────────────────────┘
```

---

## 2. Статусы верификации (`VerificationStatus`)

| Статус | Описание | Код возврата CLI |
| :--- | :--- | :---: |
| `VALID` | Все криптографические проверки пройдены, сертификат доверен согласно политике | `0` |
| `INVALID` | Нарушена целостность: хэш контента не сошелся, подпись повреждена | `1` |
| `UNTRUSTED` | Криптография сошлась, но сертификат подписанта отсутствует в TrustStore | `2` |
| `NO_MANIFEST` | В медиа-файле отсутствует C2PA манифест | `3` |
| `UNSUPPORTED` | Формат файла или версия манифеста не поддерживается | `4` |
| `ERROR` | Ошибка парсинга или внутренняя ошибка выполнения | `4` |

## 3. Политики верификации (`VerificationPolicy`)

`VerificationPolicy` определяет строгость требований к валидации:

### Предустановленные профили:
1. `VerificationPolicy.permissive()`:
   - Доверие к криптографической валидности подписи, независимо от наличия CA в TrustStore (`require_trusted_signer=False`).
   - Допускаются просроченные сертификаты (`allow_expired_certs=True`).
   - Не требуется обязательная метка времени (`require_timestamp=False`).
2. `VerificationPolicy.standard()` (По умолчанию для большинства production-систем):
   - Требуется доверенный подписант из TrustStore (`require_trusted_signer=True`).
   - Запрещены просроченные сертификаты (`allow_expired_certs=False`).
   - Метка времени TSA опциональна (`require_timestamp=False`).
3. `VerificationPolicy.strict()`:
   - Требуется доверенный подписант (`require_trusted_signer=True`).
   - Обязательна валидная доверенная TSA-метка времени (`require_timestamp=True`).
   - Запрещены любые предупреждения (`fail_on_warnings=True`).

---

## 4. Управление доверием (`TrustStore`)

В релизе v0.1 TrustStore работает в локальном изолированном режиме (без автоматических сетевых запросов):
- Загрузка сертификатов из отдельных PEM-файлов или PEM-строк (`TrustStore.from_pem()`).
- Загрузка директорий доверенных сертификатов (`TrustStore.from_directory()`).
- Раздельное хранение сертификатов подписантов (Claim Signers) и центров штампов времени (TSA).
- Сверка отпечатков SHA256 и цепочек X.509.

---

## 5. Человекочитаемое объяснение (`VerificationResult.explain()`)

Метод `explain()` формирует структурированное текстовое заключение на русском языке:
- Общий вердикт (Действителен / Недействителен / Не доверен / Отсутствует манифест);
- Подробности о подписанте (Имя, Организация, Издатель сертификата);
- Статус целостности и цифровой подписи;
- Предупреждения и ошибки с рекомендациями по устранению.
