# Политика безопасности (Security Policy)

Команда **c2pax** уделяет первостепенное внимание безопасности цифрового контента, криптографической устойчивости и защите персональных данных.

---

## 1. Поддерживаемые версии

Мы выпускаем обновления безопасности и исправления для следующих версий:

| Версия | Поддержка безопасности |
| :--- | :--- |
| `0.1.x` (текущая) | :white_check_mark: Поддерживается |
| `< 0.1.0` | :x: Не поддерживается |

---

## 2. Сообщение об уязвимостях (Responsible Disclosure)

Если вы обнаружили потенциальную уязвимость в безопасности `c2pax`:

1. **Не создавайте публичный GitHub Issue.**
2. Направьте конфиденциальный отчет через [GitHub Private Vulnerability Reporting](https://github.com/denis-ershov/c2pax/security/advisories/new) или свяжитесь с мейнтейнерами по электронной почте: `security@c2pax.dev`.
3. Пожалуйста, включите в отчет:
   - Описание типа уязвимости (например: обход проверки подписи, подделка манифеста, отказ в обслуживании / DoS, утечка ключей).
   - Пошаговые инструкции или минимальный PoC (Proof of Concept) для воспроизведения.
   - Оценку потенциального воздействия на системы пользователей.

Мы подтвердим получение вашего отчета в течение **48 часов** и предоставим информацию о сроках выпуска патча.

## 3. Архитектурные принципы безопасности c2pax

При интеграции SDK в продакшен-системы необходимо учитывать следующие фундаментальные принципы:

### 3.1. Разделение декларативных данных и криптографического доверия
- Метод `c2pax.inspect()` возвращает **только задекларированную** информацию (автор, инструменты, промпты, история), без подтверждения подлинности.
- **Никогда не принимайте бизнес-решений о доверии к контенту** на основании одного лишь вызова `inspect()`.
- Для проверки подлинности, целостности хэшей и валидности сертификатов всегда используйте `c2pax.verify()`.

### 3.2. Управление доверенными сертификатами (TrustStore)
- По умолчанию манифест может быть подписан валидным самоподписанным сертификатом, что защищает от искажения при передаче, но не доказывает личность издателя.
- Для проверки издателя настраивайте `TrustStore` с авторизованными корневыми сертификатами вашей организации или доверенной экосистемы.

### 3.3. Защита закрытых ключей (Private Key Security)
- Закрытые ключи подписантов никогда не должны сохраняться в открытом кодовой базе, логах или незащищенных конфигурациях.
- В объектах `Signer` закрытые ключи автоматически маскируются (`***REDACTED***`) при вызове `repr()` или строковой сериализации.
- В высоконагруженных и критичных средах рекомендуется использовать выделенные HSM или KMS для операций подписания.

### 3.4. Защита от атак отказа в обслуживании (DoS & Resource Limits)
- Адаптер `AssetSourceAdapter` не загружает большие потоки целиком в память при наличии seekable-дескрипторов.
- Обход графа происхождения (`ProvenanceGraph.ancestors()` / `descendants()`) аппаратно защищен от циклов (`CyclicProvenanceError`) и имеет ограничение максимальной глубины (`max_depth=512`) для предотвращения переполнения стека.

## 4. Контроль цепочки поставок (Supply Chain)

- Все релизы пакета подписываются и публикуются с генерацией Provenance-аттестаций.
- Все зависимости проходят регулярный аудит безопасности (`pip-audit`, `Dependabot`, `Bandit`).
